# AI 사용자 여정 테스트 결과 (2026-09-28)

## 범위와 환경

- 대상 코드: `edfa971` (`feat: complete shop payment and order management flows`)
- 방법: 임시 GNUCMS 복사본의 **웹 설치 화면**을 Chrome/Puppeteer로 진행한 뒤, 같은 임시 사이트에서 관리자 설정, 회원 행동, 주문 처리를 실제 화면으로 확인했다. 결과 화면과 테스트 DB의 상태를 함께 확인했다. 여기서 `설치`는 공개 사이트 배포를 뜻하지 않는다.
- 환경: PHP 8.4.1, 로컬 웹 서버, **격리된 MySQL 테스트 DB**, 저장소와 분리한 임시 애플리케이션 복사본. 기존 `config/config.php`, 운영 DB 및 기존 `storage/` 데이터는 사용하지 않았다. 테스트 DB는 종료 후 삭제했다. 임시 복사본의 정확한 경로와 DB 이름은 당시 기록하지 않아 현재 특정할 수 없다. Chrome 자동화용 `puppeteer-core`는 `/tmp/gnucms-ai-browser/`에 설치했으며 이는 GNUCMS 설치 위치가 아니다.
- 이메일 인증은 로컬 발송 캡처로 확인했다. 주소 검색은 외부 우편번호 SDK 응답을 브라우저에서 모의했다. 무통장입금 계좌와 토스페이먼츠 인증 정보는 테스트용으로 설정했다. 실제 송금이나 실결제는 발생하지 않았다.
- 테스트 데이터: 관리자 1명, 이메일 인증 회원 1명, 게시판 1개, 게시글·댓글 각 1개, 2단계 상품 분류, 상품 1개, 무통장 주문 3건. 카드 결제창 취소는 주문을 만들지 않았다.

## 실제 카드 승인·환불을 끝까지 테스트하려면

토스페이먼츠는 테스트 키로 결제해도 실제 금액이 청구되지 않지만, 일반 카드 결제창에서는 카드 인증을 완료해야 결제 승인에 필요한 거래가 생긴다. [토스 테스트 환경 안내](https://docs.tosspayments.com/guides/v2/get-started/environment)와 [테스트 방법 FAQ](https://docs.tosspayments.com/blog/how-to-test-toss-payments)에 따르면 국내 카드용 공용 테스트 카드번호는 제공되지 않는다. 카드 정보나 인증 수단을 채팅에 보내지 말고 테스트 결제창에서 카드 소유자가 직접 입력해야 한다.

현재 GNUCMS의 토스 테스트 환경은 공식 샘플 키를 자동 적용한다. 자체 테스트 상점의 거래 내역까지 확인하려면 [토스 개발자센터의 API 개별 연동 테스트 클라이언트 키·시크릿 키 한 쌍](https://docs.tosspayments.com/reference/using-api/api-keys)과 해당 상점 접근 권한이 필요하다. 다만 현행 코드는 테스트 환경 저장 시 샘플 키로 덮어쓰므로, 자체 테스트 키 사용을 지원하는 변경도 먼저 필요하다. 라이브 키나 실제 청구 권한은 이 검증에 필요하지 않다. 카드 인증이 끝나 승인 거래가 생기면 같은 테스트 거래에 대해 전체·부분 취소 API와 GNUCMS 주문·원장·재고 상태를 대조할 수 있다. 테스트 키 접근 정책을 사용 중이라면 테스트 서버의 공인 IP도 허용해야 한다.

## 남은 검증

1. PG별 샌드박스 승인·거절·타임아웃·전액 및 부분 환불을 각 결제사의 인증 수단으로 끝까지 검증한다. 이 문서의 토스 테스트창 진입은 승인 성공을 뜻하지 않는다.
2. 재고 동시 주문, 여러 옵션·추가옵션, 배송비 경계값, 관리자·회원 권한 교차 접근, 주문 취소 직후 콜백과 같은 조합을 별도 자동 시나리오로 검증한다.

격리 테스트 DB와 브라우저 임시 파일에는 계정 비밀번호·세션·메일 인증 링크가 포함될 수 있어 저장소에 추가하지 않았다. 기존 작업 트리의 `storage/tmp/` 미추적 파일은 건드리지 않았다.

## 추가 검증: 다섯 PG의 AI 주문 경로

토스 한 곳만이 아니라 **KG이니시스, NHN KCP REST API, NHN KCP 기존 TCP/IP, 토스페이먼츠, 나이스페이먼츠**를 같은 회원 카드 주문으로 검증했다. 개발 사이트 `https://gnucms.charmgen.com`의 설정은 읽기 전용으로 확인했다. 다섯 PG 모두 테스트 자격정보가 저장돼 있고 KCP 기존 방식 모듈도 설치돼 있다. 현재 신규 주문의 선택 PG는 나이스페이 테스트 환경이다. 이 확인 과정에서 개발 사이트의 PG 설정이나 주문 데이터를 바꾸지 않았다.

| --- | --- | --- | --- | --- | --- |
| 개발 사이트 테스트 설정 준비 | 확인 | 확인 | 확인, 모듈 설치 | 확인 | 확인 |
| 회원 카드 주문서 생성·결제창 주문번호/금액·인증 취소 후 새 결제번호 | 통과 | 통과 | 통과 | 통과 | 통과 |

¹ 이니시스는 기존 `PayProReturn.cjs`에서 INIPayPro 브라우저 콜백을 검증했다. 새 `PaymentWindows.cjs`는 나머지 네 결제창의 SDK 호출을 Chrome에서 검증한다. 브라우저 검증에서는 외부 SDK를 로컬 모의 스크립트로 바꿨다. 따라서 이 결과는 카드사 인증 성공을 의미하지 않는다.

새 `AllProviderCheckoutTest.php`는 다섯 PG의 주문서·결제창·인증 취소 재시도를, `DirectProviderFlowTest.php`는 다섯 **실제 어댑터 코드**와 모의 PG 응답으로 승인·회원 취소·전액 환불·재고 복원을 검사한다. 별도의 MySQL 테스트 DB에서 수행했고 개발 사이트 운영 DB를 테스트에 사용하지 않았다. 결제사별 인증 응답을 모의했으므로 **PG 외부 시스템이 승인했다는 증거가 아니다**. KCP 기존 TCP/IP 방식은 구현상 전액 취소만 지원한다.

이 변경의 관련 PHPUnit 5개 파일은 **50개 테스트·695개 assertion 모두 통과**했다. 새 두 기능 테스트는 그중 6개 테스트·77개 assertion이다. Chrome 브라우저 픽스처는 새 `PaymentWindows.cjs`를 포함해 **10개 파일 모두 통과**했다. 앞에서 기록한 전체 PHPUnit 1,355개 통과는 이전 커밋 기준이며, 이번 추가 변경 뒤 전체 테스트를 다시 실행한 결과로 읽어서는 안 된다.

주문서의 카드 선택 항목에는 현재 결제사 이름을 함께 표시하도록 바꿨다. AI나 사람이 어느 PG에서 인증하는지 명확히 확인할 수 있다. 상품의 `바로 주문하기`, 회원정보와 이전 주문 배송지 자동 채움, 단일 카드 선택은 이미 제공된다. 첫 주문에는 실제 배송에 필요한 수령인·주소를 입력해야 한다.

### 실제 승인 검증을 완료하는 조건

현재 다섯 PG는 모두 **일반 신용카드 인증 결제**다. AI가 주문 내용과 결제 요청을 입력할 수 있어도 카드사 또는 결제수단의 최초 인증 결과가 있어야 GNUCMS 서버가 PG 승인 API를 호출한다. 상점 관리자 권한이나 ChatGPT 데스크톱 권한을 주는 것만으로 카드 소유자 인증을 생략할 수는 없다. 예를 들어 [토스의 테스트 환경](https://docs.tosspayments.com/guides/v2/get-started/environment)은 승인 거래가 가상이지만 [공용 국내 테스트 카드번호를 제공하지 않는다](https://docs.tosspayments.com/blog/how-to-test-toss-payments). 나이스페이 [테스트 계정 거래도 당일 23:30에 일괄 취소](https://developers.nicepay.co.kr/docs/intro/)된다. 각 PG의 테스트 결제창에서 카드 소유자가 인증을 완료한 뒤, 주문 `결제 완료`와 PG 거래를 대조하고 회원 취소로 실제 PG 전액 취소를 확인해야 한다. 부분 취소는 이니시스·KCP REST·토스·나이스페이의 관리 경로에서 별도로 확인한다.

AI가 후속 주문을 카드 재인증 없이 실행하게 하려면 고객이 최초에 명시적으로 등록한 결제수단을 사용하는 **위임/빌링 계약과 PG별 토큰 연동**이 필요하다. 현재 일반 카드 결제 연동에는 이 기능이 없다. [토스의 빌링 가이드](https://docs.tosspayments.com/guides/billing/overview)는 최초 본인인증으로 빌링키를 발급하고 이후 승인에 사용하는 구조와 별도 계약을 설명한다. 각 PG의 계약·지원 범위를 확인한 다음 고객별 사용 범위, 금액 한도, 취소·철회, 중복 주문 방지까지 설계해야 한다. 일반 카드 결제 테스트의 성공만으로 AI의 무인 승인을 보장할 수 없다.
